# Ревью кода Aeros Engine

Дата: 2026-09-13. Обзор: `aeros/src/main.cpp` (~1540 строк), `aeros/src/kernel.cu` (477 строк), `aeros/src/flow_params.h`, `build.bat`, `.vscode/tasks.json`, структура репозитория.

Проект: визуализация обтекания STL-модели потоком. STL → вокселизация → SDF (BFS от поверхности) → загрузка на GPU; частицы и линии тока адвектируются по синтетическому полю скоростей (набегающий поток + отталкивание от SDF + вихревая дорожка по Струхалю); давление — по Бернулли из того же поля; lift/drag — интегрированием по треугольникам. Есть CPU-фолбэк для всей физики.

---

## ✅ Исправлено в этом коммите

### 1. Порча памяти при изменении числа частиц (критично)
Слайдер `Count` менял `numParticles` (100…200 000), но векторы `particlePositions/particleColors` и GL-буферы оставались старого размера. До отпускания слайдера:
- CPU-путь писал за пределы `std::vector` → heap corruption;
- `updateParticlesCUDA` делал `cudaMemcpy` на `n*3` флоатов поверх вектора меньшего размера → та же порча кучи;
- `glDrawArrays(..., numParticles)` читал за пределами VBO.

**Фикс:** введён `particleDrawCount` — фактическое количество аллоцированных частиц. Обновление физики и отрисовка работают только с ним; перевыделение происходит в `initParticles()` при отпускании слайдера (`ImGui::IsItemDeactivatedAfterEdit()`) или по кнопке Reset. Бонус: если `loadModel()` не удался, `particleDrawCount == 0` и цикл физики больше не выполняется по пустым векторам (раньше это тоже была порча памяти).

### 2. ASCII-STL вообще не загружался (критично)
Определение формата: читались 4 байта в `char header[5]` и сравнивалось `strncmp(header, "solid", 5)`. Из-за нуль-терминатора на 4-й позиции сравнение **никогда не было истинным** — все ASCII-файлы уходили в бинарный парсер, где счётчик треугольников читался из текста → гигантский `nt` → бесконечный цикл чтения мусора до исчерпания памяти (воспроизведено на тесте: процесс уходил в OOM).

**Фикс:** надёжная эвристика по размеру файла — бинарный STL имеет размер ровно `84 + 50 * nt` байт; всё остальное парсится как ASCII. Проверка по слову "solid" ненадёжна в принципе: бинарные файлы тоже могут начинаться с "solid" в заголовке — эта логика проверена тестом:
- все STL из репозитория (бинарные) парсятся идентично старому коду (108/2268/36/1788/432 вершин);
- ASCII-файл → 6 вершин, корректно;
- бинарный файл с заголовком "solid..." → корректно распознан как бинарный.

### 3. Смешение единиц в SDF (важно, влияло на картинку)
Поле расстояний строится в **вокселях** (поверхность = ±0.5, шаг BFS = 1), но сравнивалось с порогами в **мировых единицах**: `d < 1.5f * cellSizeX`, `expf(-d / (3.0f * cellSizeX))` и т.д. Следствие: зоны влияния модели (отталкивание потока, «горячая» окраска у поверхности, коллизии) зависели от абсолютного размера клетки. Например, при `cellSize = 0.05` фактор отталкивания `exp(-d/0.15)` почти нулевой уже на 1 клетке — модель «не работает» на мелкой сетке; при `cellSize = 1.0` — зона в 10+ клеток.

**Фикс:** `sampleSDF()` (kernel.cu) и `sampleSDFCPU()` (main.cpp) теперь переводят расстояние в мировые единицы (`d * cellSize`). Все существующие пороги (1.5, 3, 4, 8 клеток) стали означать именно клетки и не зависят от разрешения сетки. `sdfNormal` не затронут (первые разности масштабируются одинаково).

### 4. Гигантский dt на первом кадре
`deltaTime` первого кадра включал время диалога выбора файла и вокселизации (десятки секунд) → все частицы телепортировались. **Фикс:** клэмп `dt ∈ (0, 0.1]`.

### 5. Мелкие фиксы
- Линии тока теперь перестраиваются и при изменении `Strouhal` и `Wake Length` (раньше только Speed/Azimuth/Elevation/Wake Strength).
- `build.bat` и `tasks.json` используют библиотеки из репозитория (`%~dp0..\libs`) вместо абсолютных путей `C:/Users/USER/Desktop/dev/libs` — сборка воспроизводима из свежего клона (путь к `vcvars64.bat` остался вашим).
- Добавлен `.gitignore`; из git убраны `bin/main.exe`, `*.obj`, `bin/imgui.ini` (файлы на диске остались). DLL и примеры STL оставлены — они нужны для запуска.

## 🔴 Осталось критичного (рекомендую следующим шагом)

### 6. `computeLiftDrag()` — каждый кадр по всем треугольникам на CPU
Вызывается в цикле безусловно (даже когда `showLiftDrag == false`): на каждый треугольник — `computeVelocityFieldCPU` с несколькими `expf/sinf`. На модели со 100k+ треугольников это десятки миллисекунд каждый кадр.
**Предложение:** считать по требованию — при изменении параметров потока (тот же механизм dirty-флагов, что у линий тока) или не чаще раза в 0.2 с; не считать при выключенном окне.

### 7. CUDA: `cudaMalloc`/`cudaFree` каждый кадр + лишние копии
`updateParticlesCUDA` (каждый кадр) и `computeVertexPressureCUDA` (каждый кадр при включённом давлении) аллоцируют и освобождают device-буферы. `pressureKernel` получает нормали (`dn`), но **не использует их** — лишние 2×N флоатов memcpy туда-обратно.
**Предложение:** персистентные буферы с `ensureCapacity(n)`; нормали убрать из сигнатуры/копирования (или начать использовать); для частиц рассмотреть CUDA–OpenGL interop, чтобы вообще не гонять позиции через хост каждый кадр.

### 8. Вокселизация O(cells × triangles), однопоточно
`insideMesh()` для каждой клетки прогоняет луч через **все** треугольники. При res=48 это ~70–100 тыс. клеток; для 100-тысячной модели — ~10¹⁰ ray-triangle тестов, минуты ожидания при каждой загрузке/Rebuild.
**Предложение (по возрастанию усилий):**
1. Предфильтр: для каждой клетки проверять только треугольники, чей AABB пересекает диапазон клетки по Y/Z (просто, даёт 10–100×);
2. `#pragma omp parallel for` по клеткам (у вас MSVC, /openmp — одна строка в build.bat);
3. Раз проект всё равно CUDA — перенос вокселизации на GPU (или BVH на CPU).

### 9. Нет проверки результата `loadModel`
При нечитаемом STL показывается MessageBox, но приложение продолжает работать с пустой моделью (пустые VAO/воксели). Лучше выходить или показывать пустую сцену с понятным экраном «Load model».

## 🟡 Расхождения CPU и CUDA (разные результаты на разных бэкендах)

| Что | CPU (`main.cpp`) | CUDA (`kernel.cu`) |
|---|---|---|
| Зона «горячих» цветов | 1.5–4.0 клетки | 1.5–3.0 клетки |
| Градиент у поверхности | `hot*(1-b)+cold*b` — горячий у стенки | `hot*blend+cold*(1-blend)` — **наоборот** |
| Признак коллизии в цвете | не передаётся в `colorForPoint` | `collided && surfDist<1.5cell` → красный |

То есть переключение Compute: CUDA↔CPU заметно меняет картинку. Стоит унифицировать (за эталон взять CUDA-версию) — в идеале вынести физику в общий заголовок, включаемый обеими сторонами.

Также:
- **Респавн частиц**: и на CPU, и в CUDA частицы переносятся на плоскость `z = minZ + 0.05` со случайными X/Y — независимо от направления потока. А `initParticlesKernel` размещает их в плоскости **против** потока. Для потока вдоль X частицы всплывают в случайных местах домена вместо входного сечения. Предложение: респавн в «входной» плоскости (центр − flowDir × offset), как при инициализации.
- **Фаза вихрей не масштабируется `timeScale`**: `flowParams.time = glfwGetTime()` — сырое время. Частицы при `Time Scale` движутся быстрее, а колебания дорожки — нет. Предложение: аккумулятор `simTime += dt * timeScale` и передавать его в `FlowParams::time`.
- Линии тока считаются `computeVelocityFieldCPU` всегда (даже в режиме CUDA) — не баг, но непоследовательно.

## 🟡 Надёжность

- **Шейдеры компилируются без проверок** (`glGetShaderiv`/`glGetProgramiv` не вызываются) — при опечатке в GLSL будет тихий чёрный экран. Нужен хелпер:
  ```cpp
  static GLuint compileProgram(const char* vs, const char* fs) {
      auto check = [](GLuint sh, bool isShader) {
          GLint ok = 0; char log[2048] = {0};
          if (isShader) { glGetShaderiv(sh, GL_COMPILE_STATUS, &ok);
                          if(!ok) glGetShaderInfoLog(sh, 2048, nullptr, log); }
          else          { glGetProgramiv(sh, GL_LINK_STATUS, &ok);
                          if(!ok) glGetProgramInfoLog(sh, 2048, nullptr, log); }
          if (!ok) { std::cerr << "GL: " << log << std::endl; MessageBoxA(nullptr, log, "Shader error", MB_ICONERROR); }
          return ok;
      };
      // ... compile, link, check each step, return program only if all ok
  }
  ```
- `setVoxelData`: `cudaMalloc/cudaMemcpy` без проверок; при машине без CUDA SDF просто не загрузится и частицы полетят сквозь модель — стоит хотя бы писать в лог/в ImGui-панель статус CUDA.
- Макросы `CUDA_CHECK*` выходят из функции **до** `cudaFree` уже выделенных буферов → утечки при ошибке. С персистентными буферами (п. 7) проблема уйдёт сама.
- `if (cp>1.0f) cp=1.0f; if (cp<-3.0f) cp=-3.0f;` — два оператора в строке без скобок (в двух местах) — легко сломать при правке.

## 💡 Идеи развития

1. **Настоящий солвер по воксельной сетке.** Сетка и SDF уже есть; LBM (D3Q19) отлично ложится на CUDA и дал бы реальное (а не синтетическое) поле скоростей, давление и силы. Это логичный следующий шаг для «Aeros Engine».
2. **Срезы (slices)**: плоскость с текстурной визуализацией скорости/давления/вихря (Q-criterion) — дёшево через фрагментный шейдер, читающий SDF-текстуру.
3. **Экспорт данных**: CSV/VTI-дамп поля и сил для проверки в ParaView.
4. **Легенда цветов** для давления/скорости в ImGui-окне.
5. Юнит-тесты хотя бы на «чистые» функции (STL-парсер, BFS SDF) — они компилируются и без CUDA/GL.

## Проверки правок

Правки этого коммита проверены так:
- новая логика STL протестирована отдельной программой (g++) на всех STL из репозитория и на синтетических ASCII/бинарных файлах — результаты совпадают со старой на бинарных и чинят ASCII;
- правки `main.cpp`/`kernel.cu` минимальны и локальны (сэмплеры, счётчик частиц, dt, триггеры пересборки);
- полный прогон возможен только на вашей машине (Windows + nvcc + CUDA-девайс): соберите `build.bat` и проверьте — при проблемах каждый фикс откатывается отдельно, см. diff коммита.
