# Оптимизация решателя LBM (v1.38.0)

Дата: 2026-10-09. Ветка: `arena/b4e17ea0-aeros-engine`.

## 0. Как измерялось

Стенд: `aeros/tests/bench_lbm.cpp`, цель `make bench` в `aeros/tests`.
Сфера радиуса 0.35 в кубе, течение вдоль X, LES включён, 150 шагов после 30
прогревочных. Печатает мс/шаг и млн обновлений ячеек в секунду.

```
cd aeros/tests
make bench                      # сетка 64^3 вокселей по умолчанию
OMP_NUM_THREADS=1 make bench    # один поток
/tmp/aeros-bench-lbm 48 200 1 1 # сетка 48, 200 шагов, тепло вкл., LES вкл.
```

Стенд **не** входит в `run-suites.sh`: он измеряет скорость, а не физику, и
на медленной машине даст другие числа без всякой ошибки в коде. Числа ниже
получены на 2 vCPU Intel Xeon 2.60 ГГц (песочница), `-O2 -march=native`,
OpenMP.

| Обозначение | Что это |
|---|---|
| `было` | `f6f48c3`/`56969f6`, то есть код до этой правки |
| `стало` | v1.38.0 |

## 1. Что дало ускорение

Структура шага до правки (замер долей на сетке 3.32 млн ячеек, 1 поток):

```
столкновение  70 %
перенос       27 %
граничные      3 %
```

### 1.1 Поиск ближайшей стенки на каждом шаге (главное)

Модель Смагоринского с демпфированием Ван Дриста требует расстояние до
ближайшей твёрдой ячейки. Оно искалось **перебором 5×5×5 = 125 соседей на
каждую ячейку каждый шаг**, плюс `expf`. Расстояние — свойство геометрии, а не
поля течения, и не меняется от шага к шагу.

Что сделано: поле `lbmWallDist` считается один раз при инициализации
двухпроходным чамфером по 6 соседям (точное манхэттенское расстояние, O(N) за
проход). Множитель Ван Дриста `(1 − exp(−d/2))` взят из таблицы `kVanDriest`
для d = 0…6 — `expf` из горячего цикла убран.

Побочная польза: расстояние стало **точным**. Прежде бралась первая найденная
стенка в порядке обхода `dz, dy, dx`, то есть для ячейки у угла тела могло
взяться расстояние по диагонали обхода, а не по нормали.

### 1.2 Три целочисленных деления на ячейку

В цикле столкновения `x, y, z` восстанавливались из плоского индекса:
`cell % Nx`, `cell / Nx % Ny`, `cell / strideZ`. Целочисленное деление —
десятки тактов. Заменено на вложенные циклы `z, y, x` с инкрементом: делений
нет вообще.

### 1.3 Пять проверок внутри равновесной функции

`computeEquilibriumFast` на каждом вызове проверял `isfinite(rho)`, `|u| > 0.3`,
`isfinite(cu)`, `isfinite(feq)` и считал `sqrtf`. Она вызывается 19 раз на
ячейку, то есть 63 млн раз за шаг на сетке 3.3 млн ячеек, и каждый раз
проверяла то, что вызывающий уже обеспечил: плотность конечна (иначе заменена
выше), `|u| ≤ 0.3` (ограничитель стоит до вызова).

Добавлено ядро `equilibriumKernel` без проверок — та же формула, но с
предусловиями вместо тестов. Все прочие места по-прежнему вызывают полную
функцию с проверками.

### 1.4 Перенос: внутренняя часть и граничная оболочка

Перенос читает для каждой ячейки 19 соседей. Прежде на каждое направление
приходилось: три вычитания, два условия сворачивания периодики, шесть
сравнений границ, три умножения на сборку индекса.

Теперь перенос разделён. Внутренняя часть (у ячейки все 19 соседей
существуют) считается по плоскому смещению `src = dest + offQ[qi]`, смещения
посчитаны один раз на шаг. Граничная оболочка из шести плоскостей — это
O(N²) ячеек из O(N³) — идёт прежним общим кодом со всеми проверками.

**Ошибка, которую это чуть не внесло.** Сворачивание периодики — это переход
на другой конец строки, а не сдвиг индекса, поэтому плоским смещением оно не
выражается. Первая версия распространяла быстрый путь на весь диапазон X при
`periodicX`, и для `x = 0` соседом становилась последняя ячейка **предыдущей
строки**. Внутренний диапазон теперь всегда с отступом в одну ячейку, а
периодику обрабатывает оболочка. Тест Пуазейля идёт с периодикой по X и по Z
одновременно и ловит ровно эту ошибку (проверено: с ошибкой профиль
разрушался).

### 1.5 Тепловой модуль: то же самое

`thermalStep` получил такое же разделение переноса, плюс семь популяций D3Q7
читаются один раз и лежат в регистрах (раньше тот же участок памяти читался
дважды: сначала сумма для T, потом каждое значение для релаксации).

**Ошибка, которую это чуть не внесло.** В тепловом модуле условие на стенке —
это условие для *соседней жидкой* ячейки: ряд `y = 1` тянет значение с `y = 0`
по Дирихле (`g = −g_opp + 2 w T_wall`), а не отражается. Первая версия быстрого
пути считала внутренние стенки адиабатическими, и при
`fixedWallTemps` ряд, соседний со стенкой, шёл по неверной формуле. Симптом:
тест проводимости давал Nu = 4.14 вместо 1.000. Исправлено ограничением
внутреннего диапазона по Y при включённых заданных температурах.

### 1.6 Что пробовали и откатили

**Раскладка SoA** (`f[q*N + cell]` вместо `f[cell*Q + q]`) — классический приём
для GPU, перенесённый на CPU. **Отвергнута измерением**: 337 мс/шаг против
320 мс у AoS на сетке 1.4 млн ячеек (1 поток). Причина: столкновение читает
все 19 направлений ячейки подряд — это 3 строки кэша на ячейку, — а при SoA
те же 19 чтений идут по 19 разным потокам с шагом в размер всего поля.
Раскладка оставлена прежней (AoS), решение записано в комментарии у `fIdx`,
чтобы его не пытались «улучшить» повторно.

## 2. Результат

Сетка 48³ вокселей → домен 160×144×144 = 3.32 млн ячеек, LES включён:

| Режим | Было, 1 поток | Стало, 1 поток | Было, 2 потока | Стало, 2 потока |
|---|---|---|---|---|
| без тепла | 499.9 мс | **254.4 мс** (1.96×) | 268.1 мс | **135.8 мс** (1.97×) |
| с теплом | 631.8 мс | **320.6 мс** (1.97×) | 332.2 мс | **176.0 мс** (1.89×) |

В млн обновлений ячеек в секунду (2 потока): 5.22 → **10.31** без тепла,
4.21 → **7.95** с теплом.

По размерам сетки (2 потока, без тепла), млн обновлений ячеек/с:

| Вокселей | Ячеек | Было | Стало |
|---|---|---|---|
| 24³ | 0.42 млн | 4.72 | **10.91** |
| 48³ | 3.32 млн | 5.18 | **10.04** |
| 64³ | 7.86 млн | 6.82 | **10.01** |

На крупной сетке выигрыш скромнее (1.45× против 2.06× на мелкой): там шаг
упирается в пропускную способность памяти, и вычислительные оптимизации уже не
помогают.

Стоимость тепла снизилась вдвое в абсолютных цифрах: было +131.9 мс/шаг,
стало +66.1 мс/шаг (1 поток).

Полный набор тестов: 390 с → **275 с**.

## 4. Что осталось несделанным

* **Слияние столкновения и переноса в один проход.** Сейчас за шаг массив
  популяций читается и пишется дважды: перенос пишет `fNext`, потом
  столкновение читает `f` и пишет `f`. Один проход убрал бы половину обращений
  к памяти. По грубой оценке это ещё до 1.5–2× на крупных сетках, где шаг
  упирается в память. Не сделано: это перестройка всего шага, включая
  граничные условия, и требует отдельного обсуждения.
* Векторизация (AVX2/AVX-512) не применялась: `f[cell*Q + q]` при Q = 19 не
  ложится на 256-битные векторы без перепаковки данных.
* На машине с 8–16 ядрами масштабирование не проверялось: в песочнице 2 vCPU.
  Замеры на 2 потоках дают ускорение 1.89–1.97×, но это не доказательство
  масштабируемости на большее число ядер.
* Граничная оболочка распараллелена, но не сбалансирована: плоскости имеют
  разный объём, а распределение OpenMP идёт по z.
